各項目に状態を付けています。**現行** は今のサイトがすでに守っている決まり、**未対応** は決まりとして採用したがまだ直していない箇所です。変更するときは各項目の「確認」で確かめます。決まりとページの都合がぶつかるときは、黙って破らずにユーザーに相談します。

# 第 1 部 作業の進め方

## A. 始める前の手順(毎回)

上から順に行い、どれかが想定と違えば手を止めてユーザーに伝えます。

**コマンドを実行する場所**: 特に書いていなければ、プロジェクトのフォルダ `Nature capital real estate/`(`docs/` と `tests/` がある場所)で実行します。リポジトリ直下には `docs/` も `tests/` もないので、そこで `grep` やテストを実行すると「0 件」や失敗になり、誤った判断につながります。

1. **読む**: `PROGRESS.md` の末尾(「次回最初に読むファイル」)、`PLAN.md`、`AGENTS.md`、この文書。
2. **場所を確かめる**: `git branch --show-current` が `develop`、`git status --short` が空であること。違えば作業前に報告する(他人の作業中の変更を巻き込まないため)。
3. **最新にする**: `git pull --rebase`。`main` の変更(毎日の `catalog.json` の自動コミットなど)を `develop` に取り込むのは、自分のコミットを push し終えて手元に未 push のコミットがないときだけにする(`git fetch origin && git merge origin/main` のあと、すぐに push)。**マージのあとに `git pull --rebase` をしない**: rebase がマージを崩し、自動コミットが別の番号で複製されて、あとで `main` とぶつかる。
4. **表示を用意する**: `docker compose up -d` を実行し、http://localhost:8000/ が開くこと(ユーザーがふだん使う確認用のサーバなので、作業が終わっても止めない)。撮影は `/__preview/` 配下を使う。ほかの URL や `python3 -m http.server` で撮るとパスワード画面しか写らず、前後比較が何を変えても「一致」になる。`maintenance/nginx.conf` を変えたときは `docker compose up -d --force-recreate` で作り直す(`nginx -s reload` では反映されない。理由は `AGENTS.md` の Commands)。
5. **基準を取る**: 変更するページを変更前に撮影する(下の例)。幅は 1440px と 500px(500px は 720px 以下なのでスマホ用の配置になる)。ページ全体が入る高さで撮る。撮った画像を一度開き、パスワード画面ではなくページが写っていることを確かめる。データ更新に触れる作業なら、テストを流して件数を控える(`python3 -m unittest discover -s tests -p 'test_forest_data.py'`)。
6. **計画を書く**: `PLAN.md` に作業をチェックボックスで書く。何を変え、何を変えないか、どう確かめるかを一行ずつ。

撮影の例。画像はリポジトリの外に保存する(リポジトリの中に置くと、次の作業で `git status` が空にならず、誤ってコミットされるおそれがある)。エージェント用の作業フォルダ(scratchpad)があればそこを、なければ例の `/tmp/ncre-shots` を使う。

```
mkdir -p /tmp/ncre-shots
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --disable-gpu --hide-scrollbars \
  --virtual-time-budget=5000 --window-size=1440,8000 --screenshot=/tmp/ncre-shots/services-1440-before.png \
  "http://localhost:8000/__preview/services/"
pgrep -fl -- "--headless"   # 撮影用の Chrome が残っていないか。何も出なければよい
```

- **高さ**: `--window-size` の高さの分だけが写る。900 にすると最初の画面しか写らず、下のほうの変更を見逃す。ページより高くすれば全体が写る(下の余白は前後で同じなので比較に影響しない)。撮った画像の下のほうにフッターが写っていることを確かめ、写っていなければ高さを増やす(森林ガイドなど長いページは 8000 では足りない)。
- **幅**: ヘッドレス Chrome は幅 500px より狭く描けない。
- **待ち時間**: `--virtual-time-budget=5000` は画像を読み終えてから撮るための指定で、これがあると同じページを 2 回撮った画像はバイト単位で一致する(§C-4 の比較の前提)。
- **付けない指定**: `--user-data-dir` を付けると Chrome が終わらなくなることがある。
- **片付け**: 残っていたら、ヘッドレスのものだけを止める(`pkill -f -- "--headless=new"`)。ユーザーがふだん使っている Chrome は止めない。`pgrep -fl "Google Chrome"` はユーザーの Chrome も表示するので、片付けの判断に使わない。
- **写らないもの**: マウスを乗せたときやキーボード操作中の見た目、開いたスマホのメニュー、開いた Q&A、幅 500px より狭い画面は撮影に写らない。それを変える作業では CSS の差分を読んで確かめ、自分でも実際のブラウザで、メニューを開いた状態とマウスを乗せた状態を見る。そのうえでユーザーにも見てもらう。
- **404 ページ**: `/__preview/404.html` で撮る。`404.html` は `<base href="/fudousanbusiness-jgx/">` で本物の `auth.js` を読むので、確認用のサーバ(`maintenance/nginx.conf`)がこの URL だけ `<base>` を `/__preview/` に書き換えて返す。撮った画像に「ページが見つかりません」が写っていることを確かめる。
- **パスワード画面**: `/__preview/` を付けない URL(例: `http://localhost:8000/`)で撮る。ヘッドレス Chrome は毎回まっさらな状態で開くので、必ずパスワード画面が写る。CSS の共通部分(`styles.css` の `.password-gate`)に触れる作業では、ページと一緒にこれも前後比較する。
- **JavaScript なしの表示**: ヘッドレス Chrome は JavaScript を動かすので、JavaScript なしの表示を確かめるときは `--blink-settings=scriptEnabled=false` を付けて撮る。
- **地図のあるページ**: 森林オープンデータのページは地図の画像をネットから読むので、変更がなくても前後の画像が一致しないことがある。差の場所が地図の中だけか、並べて見て確かめる。

## B. ガードレール(破らない)

- **ブランチ**: push は `develop` だけ。`main` には直接 push しない(push すると本番に出る)。コミットと push の前にユーザーに確認する。
- **触らない場所**: `archive/`、`dist/`、リポジトリ直下の別プロジェクト(`jcredit-creation-system/` `jgx-hp/` など)。
- **変えない値**: Google フォームの URL、プライバシーポリシーのリンク、ページの URL とファイルの置き場所。
- **文言は変えない**: デザインの作業では本文・見出し・ボタンの文言を変えない(文言の見直しは別の作業として行う)。直したい文言を見つけたら `PLAN.md` に書いて残す。
- **1 つの変更に 1 つの目的**: 見た目を変えない整理(名前の付け替え、並べ替え)と、見た目を変える修正を同じコミットに入れない。
- **見た目を変えない整理は、前後で同じ画像になること**を確かめる(§C-4)。
- **共通部分は全ページそろえる**: ヘッダー・フッターは 12 個の `index.html` と `docs/404.html` に直書きなので、変えたら全部を同じように直す。リンクと画像の `../` の数はページの階層に合わせる。ただし `docs/404.html` は `<base href="/fudousanbusiness-jgx/" />` でリンクの基準を固定しているので、`../` を付けない。今あるページ間の違い(第 3 部 §14 の未対応)は、頼まれた変更と同じコミットでそろえない。
- **削除**: `rm -r` / `rm -rf` は毎回ユーザーの確認が要る。消すのは自分が作ったものだけ、名前を正確に指定する。共有の場所でワイルドカード(`*`)を使って消さない。
- **強制系のコマンドを使わない**: `git push --force`、`git reset --hard`、`git checkout -- .`。
- **新しい道具を持ち込まない**: ビルドの仕組み、npm のパッケージ、CSS フレームワーク、JS ライブラリを足さない。このサイトはビルド無しの静的 HTML である(`AGENTS.md`)。

## C. 進め方のコツ

1. **先に原因をコードで確かめる**。見た目の不具合は、効いている CSS ルールを `path:行` で特定してから直す。推測で上書きのルールを足さない(上書きを重ねると次の不具合の元になる)。
2. **直すのは狭く**。作業中に見つけた別の問題は `PLAN.md` に書き、その場では直さない。
3. **影響範囲を調べる**。クラス名を変える・消すときは、`grep -rn "クラス名" docs/` で全ページと全 CSS・JS を確かめる(JavaScript もクラス名で要素を掴んでいる。第 3 部 §16)。結果が 0 件のときは、`ls docs` で実行場所が正しいことを確かめてから「使われていない」と判断する。
4. **前後比較**。同じ条件で撮った前後の画像を `cmp before.png after.png` で比べる。一致すれば、写っている範囲の見た目は同じ。違えば画像を並べて見て、意図した差だけか確かめる。変更が影響するページをすべて、両方の幅で比べる。
5. **確認の結果は、そのコマンド自身の終了コードで判断する**。`| tail` などをつなげると失敗が隠れる。
6. **見た目を変えない整理と、見た目を変える修正が両方ある作業**(例: ボタンの名前を BEM に変え、色も直す)は、先に整理だけをコミットし、前後の画像が一致することを示す。そのあと、見た目の修正を別のコミットにする。
7. **終わったら**: 第 2 部 §11 の確認を行い、撮影で使った Chrome が残っていないことを確かめ、`PROGRESS.md` の末尾に「やったこと」と「次回最初に読むファイル」を書く。確認用のサーバ(`docker compose`)は止めない。

# 第 2 部 デザインの決まり

## 1. このサイトは何のためにあるか

山林所有者が、自分の山について**判断できる状態になる**ための場所です。物を売るサイトではありません。読み手には高齢の方が多く、相続や管理は急いで決めることではありません。

そのため、このサイトでは**行動を急がせるより、分かることを増やす**ほうを優先します。相談は「読んだ結果、必要だと思った人が迷わず申し込める」状態にしておけば十分です。

## 2. ページの 3 つの役割

ページごとに、装飾をどこまで使ってよいかが変わります。

| 役割 | ページ | 使ってよいもの |
| --- | --- | --- |
| 伝える | トップ(`docs/index.html`)、サービス一覧(`services/`)、各対象者の入口(`services/satoyama-real-estate/`、`services/forest-planning-tool/`、`partners/`、`about/`) | 写真、写真の上の文字、飾りのブロック 1 つまで |
| 読む | 森林を知る(`forest/`)、ガイド(`forest-guide/`)、お悩みから探す(`concerns/`)、持続可能な森林経営(`forest/sustainable-forestry/` と `en/`)、`404.html` | 図版。飾りは使わない(404 は図版も使わない) |
| 道具 | 森林オープンデータ(`forest-data/`) | 地図と表。飾りも写真も使わない |

- 確認: 新しいページを作るとき、まずどの役割かを決めてから組む。

## 3. 最初の画面で伝えること

ページを開いてスクロールせずに見える範囲で、知らない人が次の 3 つに答えられるようにします。

1. **だれ向けか**(例: 山林をお持ちの方へ)
2. **何のページか**(例: さとやま不動産 — 山林・里山の管理と出口整理)
3. **読むと何が分かるか、何が得られるか**(気分ではなく中身。例: 初回のインタビューは無料)

見出しは気持ちに訴える一文でよいですが、そのすぐ下に仕組みを一文で書きます。

- 状態: さとやま不動産のページは満たしている(現行)。トップは「山林をお持ちの方」という言葉と「初回無料」が最初の画面にない(未対応。文言を足すことになるので、デザインの手直しではなく文言の見直しのときに行う。スマホ幅ではヘッダーの「山林をお持ちの方」もメニューの中に隠れる)。
- 確認: 最初の画面より下を手で隠し、知らない人が 3 つに答えられるか。

## 4. 行動の示し方

**目立つボタンは 1 画面に 1 つ**にします。目的は売り込みではなく、迷わせないことです。英国政府のデザインシステム(GOV.UK)も、主なボタンを 1 ページに複数置かないよう定めています。理由は「主な行動が 2 つ以上あると、それぞれの効果が弱まり、次に何をすればいいか分かりにくくなる」ためです。

- **塗りのボタン**はその画面の主な行動 1 つだけ。2 つ目は枠線のボタンか文字リンクにする。
- **トップのヒーロー**は「さとやま不動産について」(読む)を塗り、「無料相談を申し込む」を枠線にする。読んでから申し込む順番が、このサイトの読み手に合っている。`styles.css` では `.button-outline` を `.button` より後ろに置く(強さが同じなので、前に置くと塗りに上書きされる)。
- **ヘッダーの「無料相談」**は全ページで同じ枠線の形にする。(未対応: トップだけ下線の文字リンクになっている)
- **相談への入口**は、ヘッダー、フッター、本文の区切り(ページの終わりなど)に置く。本文のすべての区切りに置かない。
- **売り込みの手法は使わない**: 画面に貼りつく追従ボタン、期限や残り数で急がせる表現、ポップアップ、閉じにくい案内。
- **ボタンの動き**: マウスを乗せたら色が変わるだけにし、浮き上がり・影・移動は付けない。すべてのボタンを同じ動きにする。(未対応: 外部リンクのボタンは銅色に変わり、影が付き、1px 動く(`styles.css:16-44`)。サイト内へのリンクの `.button` と `.contact-button` には、マウスを乗せたときの変化がない)
- **サービス一覧**(`services/index.html`)は、3 枚のカードそれぞれに塗りのボタン「サービスを見る」があり、1 画面に塗りが 3 つ並ぶ。別のページへの移動なので、文字リンクの形にする。(未対応)
- 文言の決まりは `AGENTS.md`(「無料相談を申し込む」/「お問い合わせをする」)に従う。
- 確認: 1 画面ずつ、塗りのボタンが 1 つ以下か。

## 6. 色

**ひとつの色には意味をひとつだけ**持たせます。

  - **役割(2026-10-22 ユーザー決定)**: 銅色は「費用と提供状況のバッジ」だけに使う。バッジは §13 で見た目を変えないと決めているので、ほかの用途から外すのが §13 とぶつからない唯一の絞り方になる。
  - **お悩みページの番号**(`styles.css` の `.concern-jump a span` と `.concern-group-title span`)は銅色の文字で、紙色 `#fbfaf7` の上で 2.77:1。`AGENTS.md` の基準 4.5 に届いていない不具合でもある。

- 文字と背景のコントラスト比は 4.5 以上(現行、`AGENTS.md`)。
- 確認: 新しい色を足すとき、その色が何を意味するかを一言で言えるか。

# 第 3 部 コードの書き方

コードの種類ごとに、組み合わせて使う 2 つの方針を決めました。選んだ理由は、このサイトで実際に起きた不具合か、起きやすい不具合を防ぐことです。既存のコードを一度に書き換えず、**触った部品から**この方針に合わせます(一度に書き換えると、見た目の差が出ても原因が追えないため)。

## 14. HTML: 意味に合ったタグ + 段階的な機能追加

**選んだもの**
- **意味に合ったタグ(セマンティック HTML)**: 見た目ではなく役割でタグを選ぶ。`header` / `nav` / `main` / `footer` の区分、ページに `h1` は 1 つ、見出しは段を飛ばさない(`h2` の次に `h4` を置かない)、一覧は `ol` / `ul`、項目と値の組は `dl`、表は `table`。
- **段階的な機能追加(プログレッシブ・エンハンスメント)**: CSS や JavaScript が読み込めなくても、文章とリンクはすべて読めて使えるようにする。JavaScript は便利さを足すだけにする。

**決まり**
- 別のページへ移るものは `<a>`、その場で何かを起こすものは `<button>`。見た目がボタンでも、移動するなら `<a>` にする(GOV.UK も開始ボタンをリンクで作っている)。
- `div` や `span` にクリックの動きを付けない。ネイティブの要素で足りるときに ARIA の属性を足さない。
- 画像には `alt`。飾りだけの画像は `alt=""`。
- 共通のヘッダー・フッターは全ページで同じ構造と同じクラスにする。違うのは、今いるページの印と `../` の数だけ(`404.html` は `<base>` があるので `../` を使わない)。(未対応: 今は次の違いがある。`docs/index.html` と `docs/forest-data/index.html` は `<header>` にクラスがなく、ほかは `<header class="site-header">`。トップのロゴのリンクは `href="#top"` で `aria-label` がなく、ほかは `href="../" aria-label="トップページへ"` など。英語版はラベルが英語。そろえるときは、それだけを目的にした別のコミットにする)
- 新しいページは、既存のページの `<head>` 一式(ファビコン、OGP、`styles.css`、`auth.js`、`nav.js`)を写して作る。

**見送ったもの**
- **テンプレートや部品の読み込み**(ヘッダーを 1 か所で管理する仕組み): ビルドか JavaScript での読み込みが必要になる。JavaScript で読み込むと、読み込めないときにナビが消える。
- **ARIA で組む独自の部品**: ネイティブの要素で足りる。「ARIA を使わずに済むなら使わない」が W3C の第一原則。

**未対応の例**: スマホ幅では、`styles.css` の `body > header .site-nav { display: none !important; }`(720px 以下)でナビが隠れ、`nav.js` がボタンを足して初めて開ける。JavaScript が動かないとスマホではナビがまったく使えない。隠すのを「JavaScript が動いたとき」だけにする(例: `nav.js` が `<html>` にクラスを付け、そのクラスがあるときだけ隠す)。

## 15. CSS: 並び順の層(ITCSS)+ BEM の名前

**選んだもの**
- **ITCSS(並び順の層)**: CSS を、効く範囲が広く弱いものから狭く強いものへの順に並べる。後に書いたものほど意図して勝つようにする。`styles.css` の中は次の順に区切る(見出しのコメントを入れる)。
  1. 設定: `:root` の色・文字の大きさ・間隔の名前付きの値
  2. 土台: `html` `body` `h1`〜`h3` `a` `img` などタグだけのルール
  3. 骨組み: ヘッダー、フッター、`main`、ページの幅と余白
  4. 部品: `.button`、`.flow-fees` など(部品ごとにまとめ、部品の中で基本 → 変化形の順)
  5. ページ: `.home-page` など、そのページだけのレイアウト(`home.css`、`forest-data/forest-data.css`、`forest-data/home-link.css` はこの層)
  6. 例外: どうしても必要な一時的な上書き(理由をコメントで書く)
- **BEM(名前の付け方)**: `部品__要素--変化形`。例: `.flow-fees`、`.flow-fees__step`、`.flow-fees__badge--free`。

**この 2 つを選んだ理由**: トップのヒーローの 2 つのボタンが同じ見た目になる不具合は、`.button-outline`(`styles.css:201`)と `.button`(`styles.css:254`)が同じ強さのセレクタで、後に書かれた `.button` が勝ったために起きた。BEM で変化形を `.button--outline` として部品の中の基本ルールの直後に置き、ITCSS で並び順を固定すれば、この種類の不具合は起きない。BEM はセレクタをクラス 1 つに保つので、`body > header.site-header .site-nav` のような強いセレクタや `!important`(今 9 か所)で勝ち負けを決める必要もなくなる。

**決まり**
- セレクタは原則クラス 1 つ。ID やタグを重ねて強くしない。ページの層だけは `.home-page .hero` のように 2 つまで。
- ページの層で部品の見た目を変えない。見た目を変えたいときは、部品に変化形を足す。
- 変化形は、同じ部品の基本ルールの直後に置く。
- `!important` を新しく足さない。
- 色・文字の大きさ・間隔は `:root` の名前付きの値を使う。新しい値を足すときは、その意味を名前で言えるようにする(第 2 部 §6)。
- `@media (max-width: 720px)` は、その部品のルールのすぐ後ろに置く(今は 15 か所以上に散っているが、まとめるとカスケードの順が変わるので、部品ごとに整理するときに移す)。
- 名前を BEM に変えるのは、その部品を直すときに部品ごと一度に行う。HTML 13 ファイル、CSS、JavaScript の該当箇所を同じコミットで変え、前後の画像が同じことを確かめる(第 1 部 §C-4、§C-6)。
- 部品の範囲は、名前の前半だけで決めない。例: `.flow-fees` の部品には、`.flow-fees-*` のほかに、バッジの `.fee` / `.fee-free`(`styles.css` 4145 行あたり)、`.flow-fees-steps b` などタグで指定した部分、ページの層での上書き `.home-page .flow-fees`(`home.css:265`、`309`)が含まれる。名前を変える前に、HTML でその部品の中にあるクラスをすべて書き出し、それぞれ `grep` する。
- タグで指定した部分(`.flow-fees-steps h3` など)をクラス 1 つの指定に変えると、セレクタの強さが変わり、HTML にクラスを足すことになる。強さが変わると、ほかのルールとの勝ち負けが変わることがあるので、前後の画像で確かめる。
- `id` と `aria-labelledby` の組(例: `id="flow-fees-heading"`)は、名前を変えるなら両方を同時に変える。
- 今ある `.home-page .flow-fees` のようなページの層での部品の上書きは未対応の例外。部品を直すときに変化形(例: `.flow-fees--compact`)に移す。

**見送ったもの**
- **カスケードレイヤー(`@layer`)**: 並び順の問題を言語で解決できるが、主要ブラウザがそろって対応したのは 2022 年 3 月から(MDN)。対応していないブラウザは `@layer` の中のルールをまるごと読み飛ばすので、1 つの指定が効かないのではなく、層に入れた装飾が全部消える。読み手には古い端末を使い続ける高齢の方が含まれうるので、失敗したときの被害が大きいこの方法は使わない。今のサイトの `clamp()` などは、対応していなくても 1 つの指定が効かないだけで済む。
- **ユーティリティ型(Tailwind など)**: ビルドが要る。手書きのユーティリティクラスは HTML 13 ファイルの重複を増やす。
- **CSS Modules などの自動スコープ**: ビルドが要る。
- **SMACSS / OOCSS**: 考え方は ITCSS と BEM に含まれる。名前の決まりは BEM のほうが厳密で、機械的に確かめやすい。

## 16. JavaScript: 控えめな JavaScript + 閉じた即時関数

**選んだもの**
- **控えめな JavaScript(アンオブトルーシブ JavaScript)**: HTML だけで成り立つページに、後から動きを足す。HTML に `onclick` などを書かない。JavaScript は状態をクラスか属性(`aria-expanded` など)で表し、見た目は CSS が決める。
- **閉じた即時関数**: 各ファイルを `(() => { 'use strict'; … })();` で包み、グローバル変数を作らない。3 ファイルとも即時関数と `'use strict'` で包まれていてグローバル変数は作っていない(現行)。書き方は `forest-data.js` だけがこの形で、`nav.js` と `auth.js` は `(function () { "use strict"; … })();` と `var` を使っている(未対応。次に触るときにそろえる)。

**決まり**
- JavaScript が掴む要素は、ID か `data-` 属性で指す。見た目のためのクラス名を掴みに使わない(クラス名を整理したときに動きが壊れないため)。(未対応: `nav.js` は `body > header` と `.site-nav` で要素を掴み、`nav-open` を付け外しする。`auth.js` は `.password-gate-error` を掴む。これらのクラス名は、JavaScript を `data-` 属性に直すまで変えない。変えるなら JavaScript も同じコミットで直し、スマホ幅のメニューとパスワード画面が動くことを確かめる)
- 画面に文字を入れるときは `textContent` と `createElement` を使う。外から来たデータを `innerHTML` に入れない(`forest-data.js` の `external()` が URL の形を確かめてからリンクを作っているのが手本)。
- 書き方は `const` / `let`、アロー関数にそろえる。`nav.js` の `var` は、次に触るときに直す。
- 新しいライブラリを足さない。`forest-data/vendor/` の Leaflet は版を固定した同梱のものだけを使う。
- `auth.js` はクライアント側の簡易なゲートで、本当の保護ではない。秘密の情報をページに置かない。

**見送ったもの**
- **フレームワーク(React など)・jQuery**: 今の 3 ファイル(合計約 200 行)に対して大きすぎ、ビルドか重い読み込みが要る。
- **ES モジュール(`type="module"`)**: ビルド無しで使えるが、ファイルが 3 つでほとんど独立しているので利点が小さい。

## 17. Python: 純粋な関数の芯 + 先にテスト

**選んだもの**
- **純粋な関数の芯と、外側の入出力**: データの変換は、入力から出力を返すだけの関数にする。ネットワークとファイルの読み書きは外側の関数だけで行う。`scripts/update_forest_data.py` はすでにこの形(`safe_url` `plain` `normalize` が芯、`fetch` と `update` が外側。`update` は現在時刻 `now` を引数で受け取れるのでテストできる)。
- **先にテスト**: 動きを変える前に、変えたい動きを `tests/test_forest_data.py` にテストとして書き、失敗を確かめてから直す。

**決まり**
- 標準ライブラリだけを使う(GitHub Actions は何もインストールせずに動かしている)。
- 取得に失敗したり、形のおかしいデータが返ってきたりしたときは、今の `catalog.json` を上書きしない(テスト `test_invalid_responses_never_overwrite_snapshot` が守っている)。
- 外から来た文字列は、HTML として扱われないよう整えてから保存する(テスト `test_html_is_not_executable`)。
- テストを弱めたり消したりして通さない。

## 18. 設定ファイル(GitHub Actions・Docker・nginx): 宣言的に + 版の固定

- 設定は「何をしたいか」を書き、手順の工夫を詰め込まない。1 つのファイルに 1 つの役割。
- 使うものの版を固定する(Actions は `@v7` など、Docker の画像は `nginx:1.27-alpine`)。`latest` を使わない。
- 権限は必要なものだけ。ローカルのサーバは `127.0.0.1` だけで受け、`docs/` は読み取り専用で渡す(`compose.yaml`)。
- ワークフロー(`.github/workflows/deploy-pages.yml`)は本番の公開そのものなので、変えるときはユーザーと内容を確かめてから `main` に入れる。`develop` で `workflow_dispatch` を動かさない(公開の手順にブランチの確認がないので、`develop` の中身が本番に出るおそれがある)。
