# AIを活用したプロダクト開発 実践ガイド

> 社内共有資料(2026-10-28 作成、2026-10-29 改訂)の写し。このサイトでの使い方は `DESIGN.md` を参照。

企画から試作、価値検証、実装、利用後の改善までを進めるための参考資料。社内の業務改善ツール、新サービスの試作、既存システムの改良などで、案件に合わせて利用する。

AIには調査・整理・提案・実装・検証を任せ、人は「誰の何を解決するか」「価値があるか」「重要な仕様をどう決めるか」を判断する。

作成日：2026年10月28日／改訂日：2026年10月29日

## 1. この資料の使い方

新規開発では全体の流れを確認し、改修では関係する工程を選んで使う。全工程の資料を毎回作り直す必要はない。成果物は短いメモでもよいが、目的、期待する動作、判断理由、検証結果を残す。

各項目は、次の状態を区別して扱う。

- **事実**：資料・利用者の行動・実測などで確認したこと
- **仮説**：これから確かめる対象者、課題、価値、利用頻度など
- **決定事項**：採用した仕様・範囲・条件と、その理由
- **実装済み**：機能や設定を作成・反映した状態
- **検証済み**：対象環境で期待した結果を確認した状態

## 2. 最初に用意するもの

1. 利用できるAI開発ツールと作業場所を用意する。
2. 対象のファイル、参考資料、既存の仕組みを整理する。
3. 誰の、どんな場面の、何を改善したいかを自然な言葉で伝える。

最初の依頼には「実現したいこと」「こだわり」「避けたいこと」「今回の対象外」を含める。社内データを扱う場合は、利用するAI・保存先・入力してよい情報の範囲を確認する。

## 3. 開発を進める11工程

工程名と順序は、末尾に記載したPIVOT動画の全体図を参照している。以下の成果物・確認条件は、社内で応用するために追加した実践案。

| 工程 | 行うこと・残すもの | 次へ進むための確認 |
|---|---|---|
| 01 コンセプト設計 | 対象者、困る場面、現在の方法、改善したい作業、対象外を短く整理する（例：Notion） | 誰のどの負担を、どう減らすか説明できる |
| 02 仕様設計 | ギャレットのUX5レイヤーを使い、目的、必要な機能・情報、優先度、利用の流れ、失敗時の回復方法を定める | 目的と要件がつながり、期待する動作が具体的 |
| 03 画面設計 | 主要画面のワイヤーフレームを作る（図中の例：Claude Design）。判断が割れる箇所は複数案で比較する | 次に行う操作、現在の状態、戻り先が分かる |
| 04 プロトタイプ実装 | 一連の操作を試せる最小限の試作を作る。仮データ・模擬処理を明示する | 主要操作を通して試せ、実連携との違いが分かる |
| 05 価値検証 | 想定利用者に使ってもらい、作業時間、完了率、再利用、不満を記録する | 継続・修正・見送りを、利用の事実から判断できる |
| 06 本番実装 | 実際のデータ・権限・外部連携を含めて実装し、シナリオに沿って検証する | 期待結果と実測があり、重要な未解決事項が明確 |
| 07 価格設計 | 原価を把握し、提供価格・利用上限を比較する。社内ツールは費用対効果と運用予算を検討する | 通常利用と多量利用の費用が分かり、価値や予算と照合できる |
| 08 デザイン精緻化 | FWA・The Webby Awards・Awwwardsなどで受賞を目指せる水準を品質目標とし、参考収集・共通ルールの整備・画面への適用・レビューを繰り返す | 独自性、視覚的な完成度、操作性が揃い、品質目標との差を具体的に説明・改善できる |
| 09 セキュリティチェック | 認証、権限、データ分離、外部送信、秘密情報の扱いを確認する | 許可されない操作が拒否され、修正後の再検証ができている |
| 10 マーケティング素材準備 | HyperFramesによる紹介動画やLP、必要に応じたPR TIMES配信などを検討する。社内では利用案内・デモ・問い合わせ先を用意する | 誰が何のために使い、どう始めるか分かる |
| 11 計測設計 | Google Analytics／Amplitude等の候補を念頭に、利用開始から完了・再利用までのイベントと集計方法を決める | 離脱や不便が見つかり、次の改善を選べる |

仕様設計やデザインの途中で学んだことは、前の工程へ戻して反映する。計測は公開直前だけの作業にせず、価値検証の段階から「何を確かめるか」を考えておく。

## 4. ギャレットのUX5レイヤーで仕様を考える

Jesse James Garrett（ジェシー・ジェームズ・ギャレット）の「UX5レイヤー（The Elements of User Experience）」を使い、UX（利用体験）を目的から見た目へ順に整理する。下の表では上から順に検討する。フレームワークの名前をAIに明示し、各層を順番に文書化する。

| 層 | 決めること | 問いの例 |
|---|---|---|
| 戦略（Strategy） | 利用者の課題と、取り組みの目的 | 誰の何を改善し、何を成功とするか |
| 要件（Scope） | 必要な機能・情報、優先度、対象外 | 今回どこまで作れば目的を確かめられるか |
| 構造（Structure） | 情報の整理と、操作の流れ | 入力から完了までどう進み、失敗時はどう戻るか |
| 骨格（Skeleton） | 各画面の配置と操作 | 何を先に見せ、何を押してもらうか |
| 表層（Surface） | 色・書体・余白・共通部品 | 読みやすさと一貫性をどう保つか |

目的を決める前に機能や見た目だけを増やさず、各層の内容が矛盾していないか確認する。

## 5. 価値・費用・利用状況を確かめる

### 価値検証

感想に加えて、実際に作業がどう変わったかを見る。対象者、人数、利用期間、回答数と分母を残す。

- 従来の方法と比べた、作業時間・手順数・修正負担
- 目的の作業を最後まで完了できた割合
- 次に同じ作業が発生したとき、再び使ったか
- 使わなかった理由、困った場面、代わりに使った方法
- 使えなくなった場合の困り度と、その理由

業務の発生頻度に合わせて再利用を見る。月次業務のツールを、毎日使われないという理由だけで低評価にしない。小規模な試行では回答の偏りも確認する。

### 費用・価格設計

AI処理、検索、保存、転送、外部サービス、保守・問い合わせ対応などの費用を整理する。利用量を少量・標準・多量に分け、失敗や再試行も含めて試算する。API等の単価には確認日と公式出典を付ける。

```text
月間処理費 = Σ（利用区分の人数 × 1人あたりの月間処理回数 × 1回あたりの実測費用）
月間費用 = 月間処理費 + 保存・転送等の費用 + 保守・運用等の費用
```

社内ツールでは、削減時間に人件費単価を掛けた参考額と、導入・教育・運用費を比較する。削減時間がそのまま現金の支出削減になるとは限らないため、創出した時間の使い道や品質面の効果も確認する。

対外サービスでは、提供価値と支払意思を確かめ、売上から費用を引いて採算を検討する。売上ゼロの場合は利益率を算出せず、必要な負担額を示す。平均費用だけでなく、多量利用時の上限・警告・停止条件も検討する。

### 計測設計

| 指標例 | 分かること |
|---|---|
| 利用開始者数と初回完了率 | 初めての利用でつまずいていないか |
| 操作段階ごとの到達率 | どの手順で離脱しているか |
| 処理の成功率・所要時間・再試行率 | 安定性と待ち時間に問題がないか |
| AI結果の修正率 | 人による確認・修正の負担が大きくないか |
| 次の利用機会での再利用率 | 継続して選ばれているか |
| 完了した作業1件あたりの費用 | 効果に対して費用が見合っているか |

指標には集計期間、分母、重複の扱いを決める。修正されなかったAI結果が正解とは限らないため、正しさはサンプルを別途照合する。

動画42:17–42:53では、**Google Analytics**と**Amplitude**を挙げ、イベント設計・タグの設置・分析ダッシュボードまでAIに依頼する例が紹介されている。導入時は「入れて」で止めず、イベント名、発火条件、属性、分母、重複排除、検証方法まで指定する。両方を必ず入れる必要はなく、必要な分析ができる構成を選ぶ。

計測に必要な最小限の情報を使い、機密情報・個人情報・認証情報を安易に分析ログへ含めない。収集目的、保存期間、閲覧範囲を決め、定期的に結果を見て改善を選ぶ。

## 6. 実装と品質確認の進め方

### 実装とレビューの役割を分ける

動画30:27–31:52では、**Claude Codeで実装し、Codexで厳しくテスト・レビューする**分担が紹介されている。さらに、Claudeの**Fableに全体計画・取りまとめを担わせ、Opus・Sonnetをサブエージェントとして並列に動かす**例も挙げられている。製品名とモデル名、計画役と実装役を区別して依頼する。

これは話者の開発例であり、常に同じ組み合わせを採用するという意味ではない。案件の難易度・品質・速度・費用・利用可能な環境に合わせて分担し、実装した内容は別の担当者やAIが異なる観点で確認する。同じ担当で見直した場合は、その範囲が分かるように記録する。

課金があるサービスでは、動画に登場する**Stripe**のような決済基盤を使う場合も、成功・失敗・重複操作を検証用の環境・データで確認する。実際の課金や送金とは分ける。

### 根深い問題は原因と選択肢を整理する

同じ不具合が繰り返される、修正が別の不具合を生む、データ構造・権限・費用に影響する場合は、再現条件、根本原因、選択肢、影響を整理してから方針を決める。合意済みの範囲内で進められる局所的な修正まで、毎回新しい判断待ちにする必要はない。

### テストシナリオを先に作る

| シナリオ | 確認すること |
|---|---|
| 正しい入力で最後まで操作する | 保存・処理・表示が期待どおりにつながる |
| 入力不足、対象外の形式、大きすぎるデータ | 理由が分かり、入力を修正できる |
| AIが判断できない、根拠が不足する | 推測で確定せず、未確認として扱える |
| 通信断、処理失敗、途中終了 | データを失わず、状態を確認して回復できる |
| 連打、再送、同時操作 | 重複処理・二重登録・不整合を防げる |
| 未ログイン、期限切れ、権限外の操作 | 許可されない閲覧・変更・実行が拒否される |
| 利用者が違う、端末が違う | 情報が混ざらず、必要な範囲で利用できる |
| 更新・切り戻し | 更新後の動作と、問題が起きた場合の戻し方を確認できる |

セキュリティ確認では、動画39:12–40:04に登場する**ペネトレーションテスト（侵入テスト）**という名前も明示し、攻撃者の観点で認証・権限・データ分離を確認する。対象・環境・許可範囲を定め、見つかった問題を修正した後で再検証する。

検証記録には、環境、入力、手順、期待結果、実測結果、残課題を残す。AIによるレビューや検証だけで安全性を保証した扱いにせず、扱う情報や影響に応じて専門担当にも確認する。

試作での確認、実装完了、本番反映、本番での動作確認は分けて報告する。公開・展開時には利用案内、問い合わせ先、障害時の対応、運用担当も揃える。

## 7. デザインを改善するときの進め方

**FWA・The Webby Awards・Awwwardsなどのデザイン賞を受賞できるくらいの水準まで、ブラッシュアップすることを品質目標にする。** 「かっこよく」「きれいに」という抽象的な依頼だけで終わらせず、目指す水準をAIに明示する。初稿で完了とせず、目標との差を洗い出し、改善・画面確認・再評価を繰り返す。

品質目標を実際のレビューに使えるよう、次の観点に具体化する。

- **独自性と世界観**：対象者・提供価値に合った表現があり、既成のテンプレートを当てはめただけになっていないか。
- **視覚的な完成度**：文字の大小と強弱、余白、配色、写真・図版、細部の位置まで意図が揃っているか。
- **操作と動きの品質**：操作の反応、画面遷移、アニメーションが理解を助け、体験全体として自然につながっているか。
- **読みやすさと使いやすさ**：情報の優先順位が明確で、文字の読みやすさ、キーボード操作、動きを抑える設定などにも配慮できているか。
- **実装の仕上がり**：スマートフォン・PCでの表示、読み込み速度、処理中・空・エラーの状態まで品質を保てているか。

複数の参考を集め、色・余白・文字・情報の優先順位など、採り入れたい要素を言葉にする。参考画像をまとめた**ムードボード（Mood Board）**と、共通の見た目・部品のルールである**デザインシステム（Design System）**を先に整える。既存のルールがあれば、それを確認してから追加・変更する。

画面設計では、情報配置を示す**ワイヤーフレーム（Wireframe）**を先に作る。本編18:38付近の全工程図には**Claude Design**が画面設計のツールとして記載されている。一方、36:29–36:36では、従来使っていた**Figma**を今回の事例では使わずに制作したと説明されており、Figmaの使用を必須条件にはしない。

比較が必要な画面や文言は、違いの分かる少数案を、ブラウザで見られる**使い捨てHTML**にする。見た目だけでなく、初回利用、処理中、空の状態、エラー、やり直しまで確認する。

### 紹介素材も、使う手段を具体的に指定する

動画40:15–40:31では、**HyperFrames**を指定して紹介動画を作る例が挙げられている。公式リポジトリではHTMLから動画を生成するフレームワークとして確認できる。同名のサービスと混同せず、後掲の公式リンクを参照する。

紹介動画では、対象者、伝えたい価値、尺、構成、実際の操作、字幕・ナレーション、配布先を先に定める。動画内で話者が示した製品は**SuperFlow**などの開発事例であり、紹介動画や計測のためにその製品を導入するという意味ではない。LP（ランディングページ）や、全工程図の**PR TIMES**など、誰にどう届けるかも合わせて設計する。

## 8. そのまま使えるAIへの依頼例

以下は社内向けに作成した依頼例。動画の発言の引用ではない。

### 企画・仕様の整理

> ギャレットのUX5レイヤーを使って整理してください。まずStrategy（戦略）を固め、その内容を前提にScope（要件）、Structure（構造）へ順に進めてください。対象者は［　］、困っている場面は［　］、現在の方法は［　］です。目的、必要な機能・情報、優先度、対象外、正常時と失敗時の利用の流れを順に整理してください。事実と仮説を分け、不足情報は未決定として残してください。

### デザインの品質向上

> FWA・The Webby Awards・Awwwardsなどのデザイン賞を受賞できるくらいの水準まで、デザインをブラッシュアップしてください。まず対象者・提供価値・参考デザインから目指す世界観と品質基準を整理し、共通のデザインルールを定めてください。その基準に照らして独自性、文字・余白・配色、操作と動き、アクセシビリティ、スマートフォン・PCでの完成度をレビューしてください。初稿で止めず、目標との差を自ら洗い出して改善を繰り返し、実際の画面で確認した結果と残る課題を示してください。

### 複数案の比較

> ［対象の画面・操作・文言］について、判断に影響する違いが分かる案を少数提示してください。利用者が実際に見る形で比較できる試作と、各案の利点・懸念点を用意してください。

### 根本原因の分析

> ［起きている問題・再現手順］を調べ、根本原因、応急処置、根本対応を整理してください。選択肢ごとの影響と検証方法を説明し、重要な設計変更が必要な場合は方針決定まで実装を保留してください。

### 検証・レビュー

> 目的と受入条件に照らして、正常系・異常系・権限・復旧を含むテストシナリオを作ってください。実行した項目と未実行の項目を分け、期待結果、実測、未解決事項を記録してください。

### 実装と独立レビューの分担

> Claude Codeで実装し、Codexに受入条件・不具合・境界条件の観点からレビューさせる分担を検討してください。Fableを計画役、Opus／Sonnetを実装役にする場合は、作業範囲・依存関係・統合責任を明示してください。利用できないツールやモデルがあれば、その旨と代替案を示してください。実際に行ったレビューと未実施のものを区別してください。

### 紹介動画の制作

> HyperFrames（公式リポジトリ： https://github.com/heygen-com/hyperframes ）を使い、［対象者］に［提供価値］を伝える［秒数］秒の紹介動画を提案してください。構成・絵コンテを整理し、実際の操作、字幕、必要なナレーション、配布先の形式を決めてから制作してください。未実装の機能を実現済みとして描かないでください。

### 計測の設計と実装確認

> Google Analytics／Amplitudeを候補に、［利用の流れ］を検証する計測設計を提案してください。イベント名、発火条件、属性、分母、重複排除、ダッシュボード、送信確認の方法をまとめてください。必要な構成を比較し、収集するデータと送信先を決めてから実装してください。
